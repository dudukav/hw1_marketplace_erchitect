# Дз1: архитектура маркетплейса 

## Распределение ответственности между доменами
1. User Domain 
* Регистрация и авторизация
* Управление персональными данными
* Определение роли (продавец или покупатель)
* Хранение профиля

2. Catalog Domain
* Создание и редактирование карточек товара
* Категориии и описание товаров
* Управление ценами и наличием
* Поиск и фильтрация

3. Order Domain
* Создание заказа
* История заказов
* Логика логистики 
* Управление статусами заказов

4. Payment Domain
* Обработка оплаты
* Подтверждение оплаты
* Поддержка предоплаты и постоплаты
* Интеграция с платежной системой

6. Recommendation Domain
* Работа с ML
* Формирование ленты рекомендаций
* Анализ интересов пользователя

5. Notification Domain
* Реакция на изменение статусов заказов
* Отправка sms и email уведомлений

## Распределение доменов по сервисам

Каждому домену соответствует собственный сервис , что позволяет:
* Изолировать каждый домен
* Определить ответственность каждого домена только за свою бизнес логику
* При изменении одного домена не затрагивать остальные 
* Масштабировать сервисы независимо
* Независимо разрабатывать сервисы разными командами

## Границы владения данными 

Каждый сервис владеет своей базой данных

1. User Service
* Users
* Credentials (регистрация и авторизация)
* Roles

2. Catalog Domain
* Products
* Inventory
* Category

3. Order Domain
* Orders
* OrderItems
* OrderStatus

4. Payment Domain
* PaymentTransaction
* PaymentStatus

6. Recommendation Domain
* RecommendationModel
* UserBehaviorData

5. Notification Domain
* NotificationLog
* DeliveryStatus

## Взаимодействие сервисов

### Синхронное (REST)
Примеры:
* API Gateway -> все сервисы
* Payment Service -> внешняя платёжная система
* Notification Service -> Email/SMS сервис

Для пользовательских операций

### Ассинхронное (Kafka)
Примеры:
* Order Service публикует OrderCreated
* Payment Service подписан на событие
* Notification Service подписан на события
* Recommendation Service подписан на события поведения

Повышает отказоустойчивость и нагрузку, снижает связность. Одна из основных задач -- поддержка постоплаты

## Альтернативные декомпозиции

### Модульный монолит

Создать единый сервис и единую базу данных, но разбить на внутренние модуля для удобства. Такой подход позволит достаточно быстро и просто разработать mvp. Но такой подход плохо масштабируем, имеет высокую степень связности и любое изменение или ошибка ведет к изменениям или поломкам в других модулях.

### Микросервисы по тезническим слоям

Разбить микросервисы не по доменам, а по функциям: авторизация, база данных, юизнес логика, уведомления. Плюсов нет. Только минусы: высокая связность, сложная поддержка, слишком много требований.

### Вывод

Предложенная архитектура выполняет основные требования: соответствует Domain-Driven Disign, хорошо масштабируется, разделенная ответственность, отказоустойчива, возможен независимый деплой, ассинхронная обработка событий

## Инструкция к запуску кода

Склонировать репозиторий (на всякий случай напишу, вдруг настолько трепетные требования)

```bash
-> git clone ...
```

Перейти в папку ```user_service```
```bash
cd user_service
```

Сборка и запуск:
```bash

-> docker build -t user_service .

-> docker run -p 8080:8080 user_service
```

Проверить (в другой вкладке терминала)
```bash
curl http://localhost:8080/health
curl http://localhost:8080/users
```
